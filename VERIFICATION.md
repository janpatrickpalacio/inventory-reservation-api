## Notes

- PGlite has a single database connection, so check 6 cannot test lock waiting or overlapping requests. Checks 8, 10, and 12 cover that against real Supabase.
- Setup problem found on the first real call: `GET /v1/items/<unknown id>` returned `500` instead of `404`. The server log showed `Database function get_item_status failed: Invalid path specified in request URL`. Cause: `SUPABASE_URL` had been copied with `/rest/v1/` at the end, and supabase-js adds `/rest/v1` again. Fix: check 3b (the app now refuses such a URL at startup) and clearer setup instructions in the README and `.env.example`.
- Stock read timing (checks 14 to 16): `get_item_status` compared `expires_at` with `now()`, the transaction start time, while its rows came from the later snapshot of the calling statement. The database diagnostic reproduced impossible numbers with the old function. This failure was **not** reproduced through the HTTP API: it needs a whole reservation to commit in the gap between the Data API's transaction start and its function call, and how often that can happen was not measured. Writes were not affected. Migration 002 reads `clock_timestamp()` inside the function, after the snapshot.
